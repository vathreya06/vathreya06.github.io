Stoneridge · Read the full story

The main project

My primary assignment is functional safety engineering for the Peregrine bus product line, working within the ISO 26262 concept phase. That means contributing to item definition (establishing the system's operational boundaries), Hazard Analysis and Risk Assessment (HARA) write-ups, and safety requirements documentation — the foundational work that everything downstream in the safety case depends on.

Improving the process

Working inside that documentation process, I kept running into the same friction: functional safety engineers spend a lot of time manually cross-referencing legacy HARAs, safety cases, and standards language (ISO 26262, ISO/SAE 21434) every time a new package needs to get written. So I self-initiated an internal AI Compliance Tool — a Dockerized Flask backend with a React frontend — to speed that up. Early versions handled LLM generation directly inside Flask, with a dual-provider abstraction layer (Anthropic and Azure OpenAI) so the tool wasn't locked to a single vendor, a CSV export path for medini analyze, and a guardrail that checks ASIL/CAL tagging for internal consistency before anything gets exported.

The architecture then went through a significant change: I migrated LLM generation out of Flask entirely and into Microsoft Copilot Studio, so generation happens inside the same conversational orchestration layer the rest of the org already uses. Flask was refactored into a purely deterministic validation and rendering service — schema validation and DOCX rendering run separately from the generation workflow.

Why the split matters

Separating "generation" from "validation and rendering" isn't just a refactor for its own sake — in a compliance-critical pipeline, you want the creative/generative part of the system isolated from the part that has to be deterministic and auditable. Copilot Studio handles the open-ended language work; Flask's only job now is to check that what comes back is structurally valid and to render it into a document, nothing more.

Standardizing across the floor

Working alongside process engineers, I applied Lean/Kaizen methods to standardize training workflows across 4 production lines and 12 machines. That meant rebuilding SOP and onboarding guides from the ground up rather than patching what existed — the end result cut documentation volume by 80% while making training more consistent line to line.

Chasing down false rejects

One testing machine was throwing false suction rejects at a rate that was eating into throughput. I gathered station data, pulled parts for sampling, and traced the issue to assembly-to-test pushdown distance that wasn't standardized across the line. Once that was fixed and the HMI/PLC logic was updated to reflect it, net rejects dropped by 50%.

Data across the shifts

I logged two months of ATS OEE (Overall Equipment Effectiveness) data across all three production shifts, tracking reject metrics and the causes behind anomalies to support engine-run troubleshooting — the kind of unglamorous data work that makes the root-cause conversations later actually go somewhere.

NPD trials

I also ran root-cause analysis and troubleshooting on New Product Development (NPD) trials for highly automated machinery, working to improve in-house production capability as new lines were brought up.
